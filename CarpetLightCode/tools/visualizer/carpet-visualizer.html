1. Purpose & use cases

Lets anyone debug, tune, and demo the carpet's real Arduino Due firmware from a browser tab, no physical car needed:

  • Confirm a firmware change does what you intended before flashing real hardware.
  • Track down a light-show or audio-reactivity bug with a controlled, repeatable signal instead of chasing it live at an event.
  • Tune audio settings (noise floor, peak threshold, AGC, hit decay/prediction) against a realistic simulated signal chain.
  • Walk a new contributor through every show/variation and the config menu without the car in front of you.
  • Demo the car's behavior remotely.

2. Architecture: a shell over real firmware

Most important thing to understand: this page does not reimplement the light shows. The same C++ compiled and flashed onto the real Due (src/*.cpp, src/*.h) is also compiled to WebAssembly (tools/wasm/build.sh) and shipped as tools/visualizer/wasm/carpet_fw.js. Loading this page boots that WASM module and runs the firmware's real setup()/loop() live, in your browser.

Every frame, the page does exactly three things:

  1. Inject simulated external input into the firmware's own memory — pot percentage, encoder step, button press, vehicle speed, and (for audio) 7 MSGEQ7 bin readings.
  2. Call the real firmware's tick function (web_tick(), a thin wrapper around real loop()) — the exact code path hardware runs.
  3. Read back the firmware's own output — the LED arrays it just computed (ropeLeds[], megabarLeds[], chinaLeds[]) — and draw them onto the on-screen car.

No show's color, timing, or audio-reactivity logic is duplicated in JavaScript for Dev Tool role — this was violated for a stretch of this project's history (all 5 shows were silently JS-reimplemented, not just one), found, and fixed: light output (every show, every config screen) now reads real WASM LED buffers (readLedsFromWasm()) with zero exceptions. If a show looks wrong here, it's wrong in real firmware too — that's the whole point of this design. See claude_dev_prompts.md's prompt 6 for the standing rule that exists specifically to keep this from regressing a third time.

Known gap: input injection is partially wired. Audio (7 MSGEQ7 bins) is fully real end-to-end. Pot/encoder/button injectors exist in the bridge (web_injectPotPercent/web_injectEncoderDelta/web_injectButtonDown/Up) but aren't called from this page's UI yet, so dragging the pot or pressing the encoder doesn't drive the real firmware yet — whatever show/config-screen the firmware booted into or was last saved on is what you'll see, regardless of what the on-screen controls show locally. A known, tracked gap, not a design choice.

3. What's real FW vs. a visualizer shortcut vs. simulated audio

Every control here falls into one of three categories:

FW writes/reads the real firmware — same effect as the physical input it stands in for. SHORTCUT is a dev convenience unique to this browser tool, no physical equivalent. SIM models real external analog hardware (the audio signal chain) the firmware reacts to but doesn't control.

Direct firmware I/O FW

  • The on-screen car and every light color — read straight from firmware's own LED buffers.
  • The Encoder/Pot knob panel and its live action table (Short/Med/Long/XL/Double, Left/Right, Pot) — dragging injects the same signals the real encoder/pot would produce; the action table describes what firmware actually does with them right now.
  • The show/variation dropdown and variation buttons — equivalent to short-pressing to cycle shows, turning the encoder to cycle variations.
  • Every "Audio config screens" entry (Noise/Peak meter, Hit decay meter, Foresight adjust, Sound reactivity toggle, Auto-peak toggle) — renders firmware's own config-mode screens.
  • The 4 VU meter bars (Bass/Mid/Treb/Full), raw-level overlay, and noise-floor/peak-threshold/auto-peak marks — all read from AudioBoard's real computed levels, not a JS approximation.
  • Peak thresh, Noise floor, Foresight, Hit prediction style, Hit decay sliders, and Mute/AGC/AutoPk buttons — call the same bridge functions the physical config menu calls; they just skip multi-press navigation (a UI SHORTCUT, but the values they set are 100% real committed firmware state).
  • Global/Headlight/China brightness sliders and Blacklight checkbox — same real brightness state the Brightness config screen adjusts.

Visualizer-only shortcuts SHORTCUT

  • The Settings menu (orientation, input-cap visibility, colorize lamps) — browser-only display preferences.
  • Zoom and Vehicle speed — camera/scene controls; vehicle speed isn't currently read by any show, reserved for future use.
  • The ▾ button-description toggle and the meter-stack's collapse — screen-space conveniences.
  • Mic / PC / File / Beats source-select buttons and the tone-generator pattern dropdown — choose/shape the input to simulated audio hardware (next section); firmware never sees "which source," only resulting simulated ADC readings.

Simulated realistic audio signal SIM

Firmware's audio code (AudioBoard.h) expects a real MSGEQ7 chip over 7 analog pins, fed by: phone/laptop speaker → open air → onboard mic/circuit → op-amp gain → chip → voltage divider → ADC. This page models that whole external chain in software (not a firmware reimplementation — modeling hardware firmware doesn't contain) so firmware's real noise-floor/peak-threshold/AGC/hit-decay logic gets exercised against an imperfect, realistic signal:

  • Source (Mic/PC/File/Beats) — the "instrument" playing the music, upstream of the phone speaker.
  • Source level — how hard that source drives the signal (its own volume knob).
  • Amplified noise — noise introduced before the phone's own volume control (hiss baked into the source).
  • Phone volume — the phone/laptop speaker's own volume, applied downstream of it. Defaults to 60%, not 100% — a real phone at a car meet is rarely maxed, exactly the "quiet source" scenario AGC/Auto-peak exist to compensate for.
  • Base noise — a noise floor added after phone volume (ambient/circuit noise, independent of source loudness).
  • Input cap — the simulated chip's input coupling capacitor (DC-blocking filter), affecting low-frequency response.
  • The MSGEQ7 simulation is driven by firmware's own real STROBE/RESET pin writes (captured via a pin-write log), never guessed timing — see tools/wasm/README.md for the datasheet-accurate model.

The bins row and raw-level VU overlay show what the simulated chip actually hands firmware; firmware's own AGC/noise-floor/peak-threshold logic then decides what to do with it, same as a real signal.

6. For developers

Repo & deployment

  • Firmware source: CarpetLightCode/src/. This visualizer: CarpetLightCode/tools/visualizer/carpet-visualizer.html. WASM build: CarpetLightCode/tools/wasm/ (run tools/wasm/build.sh after sourcing tools/wasm/emsdk/emsdk_env.sh to rebuild tools/visualizer/wasm/carpet_fw.js after any firmware change).
  • Local use: open carpet-visualizer.html directly from disk (file://) — WASM is base64-inlined into the built .js, no local server needed.
  • CI deploy: .github/workflows/deploy-visualizer.yml publishes to GitHub Pages on every push, one subfolder per branch: https://two-x.github.io/TheFlyingMagicCarpet/<branch-name-with-/-replaced-by-->/carpet-visualizer.html. The header's top-right text (branch @ commit - time) confirms what's live on a deployed copy; stays literal placeholder text locally/undeployed.
  • Quick-reference card generator: tools/gen_cheat_sheet_card.py (python3 tools/gen_cheat_sheet_card.py, requires pip install python-docx) regenerates cheat_sheet_card.txt/.docx at the repo root — a print-ready control-box sticker (6×1.5in) covering shows/variations/config menu/buttons. Edit the CELLS list in that script (not the generated files), then re-run.

Adding or modifying a light show / variation

Every show is a small class in src/*Show.h implementing the LightShow base (src/LightShow.h):

  • void start() — called once when the show becomes active; reset per-show state here.
  • void update(uint32_t timeMs) — called every loop() iteration; write colors into carpet->ropeLeds[]/megabarLeds[]/chinaLeds[].
  • uint8_t variation() / const char * variationName() — current variation index and short display name.
  • Register a new show in CarpetLightLogic.cpp's ShowMode enum and makeShow(); a new variation is usually another entry in that show's own enum Variation plus a case in variationName() — encoder cycling/wraparound is generic, no change needed.

Inputs available to a show (all real, all in AudioBoard.h unless noted):

  • Per-band audio levels — AudioBoard::getBandNormalPercent(band) (filtered "current level" every show should react to), getBandHitPercent(band) (a hit starts flat at 100%, holds 75ms, then — if still ongoing — eases to a 90% sustain floor over 25ms and holds there, so a long tone isn't pinned at 100%; on end, decays from whatever it was holding, not always 100%, at the configured hit-decay rate), getBandRawPercent(band), getBandRmsPercent(band), and edge flag AudioBoard::NewBandHit(band) (fires once per real hit onset — prefer over hand-rolling a threshold check, which can miss closely-spaced hits). band: BandBass/BandMidbass/BandMid/BandTreble/BandFull. Per-bin equivalents (getBinNormalPercent/getBinHitPercent/getBinRawPercent/getBinRmsPercent/NewBinHit, taking an AudioBin: FreqBin0..FreqBin6) exist for a single raw MSGEQ7 bin instead of a whole band's max — see pixel_war's treble/mid triggers in BumpingAudioShow.h.
  • Fixture geometry — carpet->ropeLeds[NUM_NEO_LEDS_ACTUAL], megabarLeds[NUM_MEGABAR_LEDS], chinaLeds[NUM_CHINA_LEDS] (CRGB/CRGBW arrays, index-addressed). Rope positional constants (FRONT/FRONT_RIGHT/RIGHT/.../FRONT_LEFT, plus clock-position aliases TWELVE/ONE_THIRTY/etc.) live in MagicCarpet.h — low index is the car's left, increasing clockwise. No (x,y) coordinate table in firmware (visualizer-only rendering concept) — real shows work purely off index/angle conventions.
  • Pot/encoder — carpet->pot->readPercent(), carpet->encoder->readPositionDelta()/resetPositionDelta().

UI conventions to stay consistent with other shows:

  • If your show's pot role is "how energetic/fast should this feel," use the shared PotEnergyTakeover helper (LightShow.h) instead of reading the pot directly — gives soft takeover and shares one committed value across Nightrider/Flame/Lighthouse.
  • For any other pot-driven live value, use the same soft-takeover pattern by hand (see EqualizerShow's potEntryPercent_/potTakenOver_) — never let a value jump the instant a show becomes active just because the pot sits elsewhere.
  • For organic, non-repeating drift (hue cycling, wandering values), use the RandomWalk pattern already duplicated in FlameShow.h/LighthouseShow.h rather than inventing a new one — this codebase prefers small per-show duplicated helpers over a shared base class.
  • Use the Timer class (Utilities.h) for time-gated cadence instead of hand-rolling millis() diffing.
  • Encoder rotation is reserved for variation cycling on every show unless you're inside a config screen — don't repurpose it for anything else within a show's own update().

After any firmware change, rebuild the WASM (tools/wasm/build.sh) before your changes will show up here — this file always runs whatever was last built, not the live source tree.
